  2. Weather as a feature

  Getting the data is easy. The Open-Meteo historical-forecast API needs no key

  3. The duration model (training/duration_model.py)

  - Approach: it's a log-normal survival model (lifelines' log-normal AFT). It
    treats the log of the alert's duration as a normal distribution. The centre
    of that distribution depends on the oblast, the hour of day, how many
    oblasts are on alert, and how long the previous alert in that oblast lasted.
    The spread is the same for every alert.
  - Why it suits the task: it predicts a full range of durations, not just one
    number. The dashboard shows the median and a 10–90% range, and updates the
    estimate as the alert goes on. For example, "it has lasted 40 min, so the
    median end is now X". All of this is a few lines of numpy/scipy, and
    training takes seconds.
  - Test results: the error of the median is 19.3 min, against 19.5 min for the
    per-oblast median, so it's barely better as a single number. The 80% range
    contains the real duration 81% of the time, which is the useful part.
  - Weaknesses:
    - The spread is the same for every alert, but a lone-drone alert and a
      massive missile attack really do differ in how uncertain they are.
    - A Weibull distribution fit the validation data slightly better, but the
      prediction code only supports log-normal.
    - In Now mode the live feed doesn't give the alert's start time, so the
      forecast can't account for how long the alert has already lasted.

  4. LSTM vs. what you have (LightGBM)

  What an LSTM would add: it learns patterns over time from raw sequences
  without hand-made features. It can also model all oblasts together and capture
  how attack waves build up.

  Why it's a poor fit here:
  - Too little data: the data has about 9k hours × 24 oblasts, and positive
    hours are rare. Neural networks overfit on that much, while gradient-boosted
    trees do well.
  - Compute: an LSTM is slow to train on a 4-core CPU, needs tuning, and gives
    different results from run to run. LightGBM trains in about 20 s.
  - Leakage risk: your current features have tests proving they only use data
    available at time t. Sequence windows are much easier to get wrong.
  - Recent evidence: on tabular and event-count data like this, boosted trees
    with lag features usually match or beat RNNs, as in the M5 competition.

  Alternatives worth considering (all cheap):
  1. Keep LightGBM and keep improving features. You're already doing this, and
     it's the right default.
  2. Hawkes process (self-exciting point process): each alert raises the chance
     of more alerts nearby soon after, and that effect fades over time. This
     matches how attack waves move between oblasts, and it has very few
     parameters. It works well as an interpretable baseline or as an extra
     feature.
  3. Logistic regression on the same features: it's a sanity check. If it gets
     close to LightGBM, the features matter more than the model.
  4. Pretrained time-series models (Chronos, TimesFM): they need no training,
     but they forecast counts rather than event probabilities, and they're
     heavier to run on a CPU. Only worth a quick comparison.

  If you want something more for the start model, a Hawkes baseline makes a good
  comparison point: about an hour of work, and it trains in seconds.
